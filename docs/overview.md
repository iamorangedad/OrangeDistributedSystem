## 背景

学习目标是做一个麻雀虽小、五脏俱全的分布式系统：能容错，也能随积压伸缩，并且能在本机把故障注入进去看结果。

另一个项目需要下单能力。Orange 把「提交一笔订单」做成独立系统，调用方通过 HTTP 集成，不把商品目录和支付做进 Orange。

## 要解决的问题

一次下单同时碰到这些约束：

- 同一个请求重试不能产生两张订单。
- 推荐服务变慢或退出时，订单仍然要成功，并明确告诉调用方结果是降级的。
- 履约可以晚于接单完成，积压升高时要增加处理能力，积压越过保护线时要拒绝新单。
- 主存储进程消失后，系统要切换到从存储，旧进程恢复后不能再写。
- 一次请求能够用同一个 `request_id` 从网关追到存储和工人。

## 目标

1. 提供 `POST /v1/orders` 与 `GET /v1/orders/{order_id}`，供另一个项目集成。
2. 在一台机器上用多个进程演示：限流、副本摘除、超时、熔断、降级、至少一次投递、死信、单主复制、epoch 隔离、按积压加减工人。
3. 每一类故障都有写明的对外结果，而不是「看当时运气」。

## 边界

Orange 负责：

- 接受订单并持久化
- 幂等
- 可选的推荐字段
- 异步履约，以及调用方提供的本机履约地址
- 主从复制与故障转移

调用方负责：

- 商品、价格、库存和购物车
- 是否允许这笔业务下单
- 履约地址上的业务动作（扣库存、通知用户等）
- 把 Orange 的 `order_id` 或自己的 `external_ref` 记在自己的数据里

第一版不包含：跨地域多活、多主写入、CQRS、Raft/Paxos、独立消息中间件、容器编排、服务网格、边缘 CDN、托管混沌平台、按 CPU 或延迟自动扩缩、调用方身份认证。能访问 `127.0.0.1:8080` 的本机进程就可以下单。

## 约束

- 部署在一台机器上，进程由监督者拉起。
- 实现使用 Python 3 标准库和 sqlite3。见 [ADR 0004](adr/0004-stdlib-sqlite.md)。
- 写入者始终只有当前 epoch 的主存储。见 [ADR 0001](adr/0001-single-leader.md)。
- 订单副本数固定为 2。弹性只加在工人上，用来消化履约积压。
- 对外集成使用同步 HTTP 加轮询。第一版不提供 webhook。见 [ADR 0005](adr/0005-sync-poll-integration.md)。

## 术语

| 术语 | 含义 |
| --- | --- |
| 调用方 | 集成 Orange 的另一个项目 |
| 订单 | 一次已接受的下单记录 |
| 任务 | 挂在订单上的履约工作，存在主存储的任务表里 |
| epoch | 单调递增的写入代际。旧代际的写入会被拒绝 |
| 主存储 | 当前唯一可以确认写入的节点 |
| 从存储 | 异步应用主存储日志的副本，可能落后 |
| 降级 | 订单已保存，推荐缺失。响应里 `degraded` 为 `true` |
| 死信 | 超过重试次数、不再自动执行的任务 |
| 见证人 | 监督者。只有它能提升新的主存储 |
| 截止时间 | 网关为一次请求规定的绝对结束时刻，向下游传递 |
